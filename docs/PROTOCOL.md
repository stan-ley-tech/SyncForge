# SyncForge REST Protocol

All requests and responses are JSON. All endpoints except device
registration require an `Authorization: Bearer <device_token>` header. Any
non-2xx response has the body `{"error": "<message>"}`.

See [`pkg/api`](../pkg/api/api.go) for the exact Go types and
[`internal/server`](../internal/server) for the handler implementations.

## Authentication model

A device's identity (`device_id`) is generated by the **client**, not the
server — see [ARCHITECTURE.md](ARCHITECTURE.md) for why. Registration
associates a bearer token with that id. The server stores only a SHA-256
hash of the token, never the token itself.

## `POST /v1/devices/register`

Register a device (or rotate its token if `device_id` already exists — the
same id, re-registered, does not fail).

**Request**

```json
{ "device_id": "b7f870cb-...", "device_name": "Alice's Laptop" }
```

**Response** `201 Created`

```json
{ "device_id": "b7f870cb-...", "device_token": "92b66bb1..." }
```

The token is returned exactly once and is not recoverable afterwards.

## `POST /v1/sync/push`

Push a batch of local ops. Idempotent: an op whose id already exists
server-side is acknowledged again with no additional effect, so retried
pushes are always safe. Every op's `device_id` must match the authenticated
device, or the request fails with `403`.

**Request**

```json
{
  "ops": [
    {
      "id": "6f497d93-...",
      "device_id": "b7f870cb-...",
      "collection": "notes",
      "record_id": "note-1",
      "type": "create",
      "payload": { "title": "hello" },
      "version_vector": { "b7f870cb-...": 1 },
      "hlc": { "physical": 1755000000000000000, "logical": 0, "node_id": "b7f870cb-..." }
    }
  ]
}
```

`type` is one of `create`, `update`, `delete` (a `delete` omits `payload`).

**Response** `200 OK`

```json
{
  "accepted": ["6f497d93-..."],
  "conflicts": [
    {
      "collection": "notes",
      "record_id": "note-1",
      "winning_op_id": "6f497d93-...",
      "losing_op_id": "c686e707-..."
    }
  ],
  "server_checkpoint": 4
}
```

`conflicts` lists every op in this batch whose version vector was
*Concurrent* with what the server already had for that record — i.e. a
real conflict was detected and resolved (see ARCHITECTURE.md), not just a
sequential edit. `server_checkpoint` is the server's checkpoint after
applying this batch.

## `GET /v1/sync/pull`

Fetch ops accepted after a checkpoint, incrementally and (optionally)
restricted to one collection.

**Query parameters**

| Param        | Default | Meaning                                             |
|--------------|---------|------------------------------------------------------|
| `since`      | `0`     | Return ops with `server_seq > since`                  |
| `collection` | (all)   | Restrict to one collection (partial sync)             |
| `limit`      | `100`   | Max ops per page                                      |

**Response** `200 OK`

```json
{
  "ops": [ { "id": "...", "server_seq": 4, "...": "..." } ],
  "next_checkpoint": 4,
  "has_more": false
}
```

Pass `next_checkpoint` as `since` on the following call. Keep paging while
`has_more` is `true`.

## `GET /v1/sync/status`

**Response** `200 OK`

```json
{ "device_id": "b7f870cb-...", "server_checkpoint": 4, "conflict_count": 1 }
```

## `GET /v1/records/{collection}/{id}`

Fetch the server's current materialized state of one record (mainly for
debugging/inspection — normal sync flows through push/pull).

**Response** `200 OK`, or `404` if the record has never been touched.

```json
{
  "collection": "notes",
  "record_id": "note-1",
  "payload": { "title": "hello" },
  "deleted": false,
  "version_vector": { "b7f870cb-...": 1 }
}
```
